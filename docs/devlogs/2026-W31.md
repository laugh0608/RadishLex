## 2026-07-27：M5-P02 首个 Fcitx5 addon 实现批次

- 审计 ABI v9、公共 C header、owned `KeyResult`/snapshot 与 personalized Rime session，确认 key、learning context、display-index selection、reset/free/shutdown 已足以表达首批 Fcitx5 输入链；本批未增加 Fcitx 私有 ABI 或修改 macOS build 38 metadata。
- 建立 `platforms/linux-fcitx5/` C++17/CMake 工程、addon/input method metadata、Fcitx engine/input context property、input panel candidate、commit 和 lifecycle 接线。候选内容与顺序只消费 Rust snapshot；数字、Space、鼠标统一回传 display index，C++ 不读取 engine index 或调用 Rime 私有 API。
- 把 FFI 调用收口为可注入的 owned C++ projection：每次调用先设置 `LearningContext`，严格校验 ABI/result version、boolean、UTF-8、candidate index/source、personalization/learning enum 和 cursor boundary，复制后立即释放 Rust result；wrapper 先阻断非 owner-thread 调用。
- 实现 addon 与未来 Linux Manager 共用的 XDG resolver：authoritative home 来自 `geteuid/getpwuid_r`，默认 data/config/state/cache 路径固定；relative/dot、symlink、错误 owner、非目录、宽权限失败关闭，product/Rime 目录使用 `0700`，userdb 使用 `0600` + `O_EXCL` + `O_NOFOLLOW`。test resolver 只在编译期开启，不读取 production fixture override。
- 新增 `./scripts/check-linux-fcitx5.sh` 并纳入仓库基线。默认模式用现有 C++17 compiler 验证 key/FFI/XDG contract；`--require-fcitx` 只在 Linux 且调用方提供既有 native-rime cdylib 时构建 addon，不下载依赖、不安装或启用输入法。
- 当前 macOS 26.5.2 arm64 只有 Apple clang 和 Docker CLI，缺失 CMake、Ninja、pkg-config 与 Fcitx5 development package。平台无关 contract 通过，但没有启动 Docker、下载依赖或取得真实 Linux/Fcitx5 编译运行证据；M5-P02 仍需真实 Linux 开发构建收口。

## 2026-07-27：M5-P02 Debian ARM64 开发构建

- 采用 Docker Desktop 的 Linux VM 建立固定 digest 的 Debian 13 ARM64 开发镜像；宿主仓库只读挂载，Cargo registry/target 使用独立 named volume，不向 macOS 安装 Linux 依赖，也不安装或启用输入法。
- 基线版本为 Rust 1.85.0、CMake 3.31.6、Fcitx5 Core 5.1.12、librime 1.13.1 和 GCC 14.2.0。启用 `native-rime` 的 `libradishlex_ime_ffi.so` 与 `radishlex.so` 均构建为 ARM64 ELF，`ldd` 确认 addon 链接 Fcitx5 Core、共享 FFI 及其 librime 依赖。
- 真实 Linux headers/compiler 暴露三个此前 Apple clang contract 未覆盖的差异：ARM64 C `char` 对 bindgen 为 `u8`，Rime adapter 因而统一使用 `std::ffi::c_char`；GCC 14 拒绝无意义的 unsigned enum 下界比较；`fcitx::Key` 不是 literal type，选择键表改为只读 `const` 初始化。
- 修正 Linux 强门禁只构建 addon target、却直接执行未构建 CTest executable 的缺口；当前默认 CMake target、addon ELF/动态依赖、FFI projection 与 XDG CTest 在同一容器内全部通过。
- 该证据只收口 M5-P02 的 Linux ARM64 编译/链接基线。容器没有 Fcitx daemon、Wayland/X11 session 或真实应用 input context，不能作为 M5-P03 桌面运行、输入或安装证据。

## 2026-07-27：M5-P02 addon-relative 开发装配与 loader 诊断

- 移除 addon 对编译期仓库 RimeData 绝对路径的运行依赖。CMake build/staged install 现在把 `radishlex.so`、sibling `libradishlex_ime_ffi.so`、三项锁定 RimeData 和两份 Fcitx metadata 形成同一开发装配；addon ELF runpath 只使用 `$ORIGIN`。
- 新增 runtime layout contract，从实际已加载的 `radishlex.so` 派生 sibling FFI 与 `radishlex-rime`，拒绝相对/非规范 addon 路径、错误文件名、缺失资源、leaf symlink、非 regular file/目录、group/other 可写 addon 目录或资源。失败不回退到仓库、工作目录或在线下载。
- 新增 `radishlex_runtime_probe`，先复用相同 layout 校验，再对 staged addon 执行 `dlopen(RTLD_NOW | RTLD_LOCAL)`；诊断只输出稳定原因类别。该 probe 证明 native dependency closure，不实例化 Fcitx Engine，也不替代 daemon/桌面 input context。
- Linux 强门禁新增 CMake install stage、sibling FFI/RimeData/metadata presence、staged `ldd`、`$ORIGIN`、动态 metadata 与字符串构建路径泄漏检查、runtime probe 和第三项 CTest。固定 Debian 13 ARM64 环境全部通过。
- macOS 平台无关 contract 继续通过；Docker 证据扩大为 ARM64 编译、staged 装配和 headless loader，仍不宣称 Fcitx daemon、Wayland/X11 或真实应用输入已验证。
